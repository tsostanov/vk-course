# Задание 9: корутины

## Отмена установки

`AppDetailsState.Content.installState` содержит одно из состояний: `NotInstalled`, `Installing(progress)` или `Installed`. Кнопка берёт подпись из состояния. После завершения она показывает «Установлено» и становится неактивной.

`AppDetailsViewModel.onInstallClick()` сразу выставляет `Installing(0)` и сохраняет результат `viewModelScope.launch` в `installJob`. Внутри выполняется `emulateInstall()`: 20 шагов по 5%, перед каждым — `delay(150)`. Состояние обновляется через `MutableStateFlow.update`. Полная установка занимает примерно 3 секунды.

Повторное нажатие вызывает `installJob?.cancel()` и возвращает `NotInstalled`. Отмена кооперативная: `delay` проверяет отмену и выбрасывает `CancellationException`. Поэтому отменённая корутина не доходит до следующего обновления прогресса или `Installed`. Исключение не перехватывается и не подавляется. Установку можно начать заново с 0%.

`viewModelScope` — родитель установки. ViewModel принадлежит записи карточки в Navigation Compose: при пересоздании Activity работа продолжается, при удалении карточки из стека ViewModel очищается и её корутины отменяются. Статус установки хранится только в этой ViewModel; повторный вход в карточку создаёт новое состояние.

## Загрузка рейтингов

`CatalogApi.getRating(id)` эмулирует запрос: `delay(1500)` и случайный рейтинг от 3,0 до 5,0 с шагом 0,1. Реальный HTTP-запрос для рейтинга не выполняется. Источник данных делегирует вызов API, а репозиторий предоставляет два метода:

```kotlin
override suspend fun loadRatingsSequentially(ids: List<String>): Map<String, Float> =
    ids.associateWith { id -> dataSource.getRating(id) }

override suspend fun loadRatingsInParallel(ids: List<String>): Map<String, Float> = coroutineScope {
    ids.map { id -> async { id to dataSource.getRating(id) } }.awaitAll().toMap()
}
```

В первом варианте следующий запрос начинается после завершения предыдущего. Во втором `async` создаёт дочернюю корутину для каждого id, а `awaitAll` ожидает результаты всех запросов. Ограничений параллельности здесь нет.

`coroutineScope` не завершается раньше своих детей. Если один запрос завершается ошибкой, остальные отменяются, ошибка передаётся вызывающей корутине. Отмена родительской загрузки также отменяет все запросы. Это проверяется unit-тестами. `GlobalScope`, отдельные независимые scope и блокирующий `Thread.sleep` не используются.

В каталоге можно по очереди нажать «Последовательно» и «Параллельно». `AppCatalogViewModel` измеряет каждый вызов через `measureTimeMillis`, сохраняет оба результата и показывает рейтинги рядом с названиями приложений. Пока выполняется один способ, обе кнопки заблокированы. При ошибке каталог остаётся доступен, отображается сообщение и можно повторить попытку. Перезагрузка каталога отменяет текущую загрузку рейтингов; очистка ViewModel отменяет все её дочерние корутины.

| Способ | Фактическое время | Ожидаемое время без накладных расходов |

| Параллельно | 1 544 мс | 1 500 мс |

Фактическое ускорение — примерно **11,77 раза**. Разница с идеальными значениями связана с планированием корутин и нагрузкой среды. Это один прогон учебной симуляции, а не статистический сетевой бенчмарк.

Дополнительно оба способа проверены через кнопки каталога на эмуляторе Pixel 10 (API 37), на списке из 12 приложений: **18 090 мс последовательно**, **1 512 мс параллельно**. В этом UI-тесте подставляется API с тем же `delay(1500)` и фиксированным рейтингом 4,2 для проверки отображения; ViewModel, Use Case и репозиторий используются настоящие.

## Как повторить замер

Из корня проекта:

```powershell
.\gradlew.bat :homework-04:testDebugUnitTest --tests '*AppRatingsBenchmarkTest' --rerun-tasks
```

`AppRatingsBenchmarkTest` создаёт настоящий Retrofit API, источник данных и репозиторий и по очереди вызывает оба метода для 12 различных id. Используются `runBlocking`, настоящие `delay` и `measureTimeMillis`, без виртуальных часов `runTest`. Сеть для этого замера не нужна: метод рейтинга эмулирован. Вывод `RATINGS_BENCHMARK` доступен в XML-отчёте `assignments/04-compose-app-list/build/test-results/testDebugUnitTest/TEST-com.example.vkcourse.applist.data.repository.AppRatingsBenchmarkTest.xml`.

Отдельный тест с виртуальным временем проверяет строгое различие алгоритмов: 18 000 мс и максимум один активный запрос для последовательного варианта; 1 500 мс и 12 одновременно активных запросов для параллельного. Эти значения служат проверкой алгоритма, а не фактическими замерами времени.

## Выводы

Для N приложений с одинаковой задержкой последовательная загрузка занимает примерно `N × 1500 мс`, параллельная — примерно `1500 мс` плюс накладные расходы. Для 12 приложений ожидаемое ускорение близко к 12 разам. Это перекрытие времени ожидания: `delay` освобождает поток, поэтому создавать отдельный поток на каждый запрос не требуется.

Рейтинги при каждом запуске случайные, поэтому сравнивается длительность загрузки одинакового набора id, а не совпадение чисел. В реальной сети неограниченное число запросов может перегрузить сервер; здесь оно выбрано по условию задания.
